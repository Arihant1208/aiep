# ADR-0017: Pre-tenant operations through narrow SECURITY DEFINER functions

- **Status:** Proposed
- **Date:** 2026-11-09
- **Deciders:** Arihant Jain (pending sign-off)
- **Spec references:** §6, §8.1, FR-001
- **Supersedes / Superseded by:** — (implements the "narrowly scoped `SECURITY DEFINER` functions" rule of
  [ADR-0006](0006-tenant-isolation-shared-database-rls.md) for the first three cases)

## Context

[ADR-0006](0006-tenant-isolation-shared-database-rls.md) puts every tenant-owned table behind RLS that is enabled
**and forced**, keyed on `app.organization_id`, which the API sets only after authentication. Three operations must
happen **before** any organization is known:

1. **Sign-in:** map a validated token's `(iss, sub)` to a `subjects` row, creating it the first time.
2. **API key authentication:** find a key by its public `key_id` to learn which organization it belongs to.
3. **Organization creation:** insert an organization and its first Owner membership when no tenant exists yet.

Two facts make this harder than it looks:

- `FORCE ROW LEVEL SECURITY` also binds the **table owner**. A `SECURITY DEFINER` function owned by `aiep_migrator`
  is still filtered by the tenant policy, so "make it SECURITY DEFINER" alone does not work.
- `subjects` is not tenant-owned (one person, many organizations), so the tenant policy cannot protect it.
  Without a rule, any service query could list every user of the platform.

## Decision

**Three fixed-purpose functions** in schema `aiep`, created in `V0001`, all `SECURITY DEFINER` owned by `aiep_migrator`,
with `SET search_path = aiep, pg_temp`, `EXECUTE` revoked from `PUBLIC` and granted to `aiep_api` only:

| Function | Purpose | How it gets past RLS |
| --- | --- | --- |
| `resolve_subject(new_id, issuer, sub, display_name, email) → uuid` | Upsert the subject for a validated token; refresh display data | Policy `definer_identity_resolution` on `subjects`, `TO aiep_migrator` |
| `find_api_key(key_id) → row` | Return the key's organization, owner, hash, scope, expiry, revocation | Policy `definer_api_key_lookup` on `api_keys`, `FOR SELECT TO aiep_migrator` |
| `create_organization(org_id, name, owner_membership_id)` | Create the organization and its Owner membership atomically | Sets `app.organization_id` to the **new** id (transaction-local) so the normal tenant policy applies, then clears it |

Rules that come with them:

- **No tenant-table policy other than `tenant_isolation` applies to service roles.** The definer policies are scoped
  `TO aiep_migrator`, the schema owner, which could disable RLS anyway, so they grant nothing new. Services never
  connect as `aiep_migrator` and reach those rows only through the functions' fixed queries.
- **`create_organization` takes the owner from `app.subject_id`**, which the API sets from authentication, never from a
  parameter. It refuses to run without a subject or inside an existing organization context. Passing an existing
  organization id fails on the primary key before any membership is written, so it cannot be used to join another tenant.
- **`subjects` access rule:** services can `SELECT` only their own row (`app.subject_id`) and subjects with a
  membership in the current organization. They have no `INSERT`/`UPDATE`/`DELETE`; writes go through `resolve_subject`.
- **IDs are UUIDv7 generated by the application** and passed in, so ID generation stays in one place (PostgreSQL 17
  has no `uuidv7()`).
- Every new pre-tenant need gets its **own** function and a line in this table (a new ADR if it changes the pattern).
  No generic "run as definer" function, no `BYPASSRLS` role.

## Consequences

**Positive**

- The tenant policy stays the only rule a service role meets on tenant tables; tests check that from the catalog.
- Each bypass is a few lines of reviewable SQL with a fixed query shape; tests cover the abuse cases (hijacking an
  organization id, calling without a subject, calling as the worker).
- No extra database role or init-script change.

**Negative / costs**

- `find_api_key` returns the secret hash to the API. That's needed (the pepper lives in the API, not the database),
  but it means the API must compare in constant time and never log the row.
- The definer policies mean `aiep_migrator` sessions see all subjects and API keys. Acceptable because that role
  already owns the tables, but it's one more reason services must never use it.
- `resolve_subject` writes on first sign-in and whenever display data changes. The API should cache the mapping
  briefly instead of calling it on every request.

**Risks and mitigations**

- *A future definer function is written carelessly* (dynamic SQL, missing `search_path`). A test asserts every
  `SECURITY DEFINER` function in `aiep` pins `search_path`; review rule: no dynamic SQL in definer functions.
- *Subject visibility leaks membership across tenants* (for example, "does this email have an account?"). The policy
  only shows co-members. Inviting by email is designed in the members endpoint (Phase 1 step 6) without revealing
  whether an account exists.

## Alternatives considered

| Option | Why not |
| --- | --- |
| A `BYPASSRLS` service role for these lookups | Forbidden by ADR-0006; a blanket bypass for three queries |
| Separate `NOLOGIN` role owning the functions, with its own policies | Function owner ≠ table owner is slightly tighter, but needs an init-script change, `CREATEROLE` and membership plumbing; with no dynamic SQL, the gain is small. Revisit if definer functions grow. |
| Non-RLS lookup tables (`api_key_lookup(key_id, organization_id)`) | Moves the same problem to another table and duplicates data |
| `subjects` with no RLS, guarded only by application code | One careless query lists every user on the platform |
| Disable `FORCE` on the tables the functions touch | Weakens the property the whole design relies on, for every query, not just these three |

## Revisit when

- More than a handful of definer functions exist, or one needs dynamic SQL (consider a dedicated owner role).
- A platform-operator or reconciler path needs cross-tenant reads (Phase 2 reconciler); it gets its own function and entry here.

## Acceptance criteria (Proposed ADRs only)

- [ ] Owner agrees that pre-tenant access is limited to these three functions and the `TO aiep_migrator` definer policies.
- [ ] Owner agrees with the `subjects` visibility rule (self plus co-members of the current organization).
